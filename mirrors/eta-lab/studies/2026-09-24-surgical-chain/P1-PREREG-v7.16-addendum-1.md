## A. `link3_screen.py` (piece C): the score_input guard accepts batch directories
- **What failed:** on the batch-2 chain, C's screen refused `mt-b2/` (`ValueError: score_input must be written inside an mt/ directory`). It **failed closed**: no `score_input.json` and no screen report were written; `mt-b2/screened.json` (C's audit record, written before the guard) was left, and `verify` then also failed closed on the missing `score_input.json`. v7.16 V4 said "no change to C is planned"; that was wrong.
- **The change (radar-kit, refuter-2 PASS #1567, landed as `941b9b8`):** the guard accepts a directory whose **whole name** matches `mt(-b[0-9]+)?` (`mt`, `mt-b2`, `mt-b3`) and refuses everything else (`raw`, `deid`, `run`, `mt2`, `mt-x`, `mt-b`, `mt-b2x`, upper case, a trailing newline, `mt` only as a grandparent); nothing else in C changes (keep rule, drop reasons, BLOCKED semantics, exit codes 0/1/3, delete-before-write, 0600). A tests-only commit adds three more refused names (`mt-`, `mtb2`, `b2`).
- **Effect on the record:** the stale `mt-b2/screened.json` is rewritten and any old `score_input.json` deleted by the re-run (F-C1), so the re-run is clean. The failed run is disclosed here and in the report.

## B. The second reader's pin is salted (from the batch-3 read on)
- **The defect (eta-refuter-2 #1559, his own to own):** a pin that is the plain sha256 of an all-zero counts file is computable by anyone who knows the drawn keys, so it **revealed an all-zero read** to a reader who saw it before locking. At r2 the linker's counts were hashed before the pin was seen; at **b2 the linker locked at 02:16:28, after the second reader's pin (06506fa7…, equal to the all-zero hash) was public**. Both reads were all zeros and each states its counts came from the text alone, so no result depends on it; the r2 and b2 gates stand as passed under the rule then in force.
- **The change (split-speaker, `a1c5cda`; linker's `verify` `5ebadbc`):** the second reader's pin becomes **sha256(salt ‖ counts-file bytes)** with a private random 32-byte salt kept until the summary (`link3_nameleak.py pin`, then `summary --second-pin --second-salt`); `summary.json` records `second_pin` and `second_salt` (and the plain hash as an audit field, which is **not** the pin); `verify` checks `second_pin` against `--second-pin` and a well-formed salt, refuses a summary whose plain hash is offered as the pin, and keeps the old plain comparison **only** for summaries without `second_pin` (r2, b2). v7.15a N2 step 2's "posts its sha256" therefore means, from the batch-3 read on, **the salted pin**.
- **Order rule for the batch-3 read (eta-refuter-2's stopgap, kept even with the salt):** **both readers lock before either posts anything**; each posts only "locked" with the file's mtime; the salted pin and the first reader's hash go up **together** afterwards. The first reader's hash is not salted and would reveal an all-zero read if posted first.
