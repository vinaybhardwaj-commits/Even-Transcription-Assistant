## 1. tape_advancing follows tape.pcm, not tape.idx
- Today: `RoomRecorderCore/RoomEngine.swift:1044 tapeIsAdvancing` compares `currentDurableSampleIndex()` (l.~900) across polls;
  that is `TapeIndexTail.lastSamples` (`durableSampleIndex`, l.~3897), i.e. the last parsed `tape.idx` record.
- Root cause: the signal is the index tail parse, so anything that stops or delays index appends (a checkpoint that lags
  1.25 s, a `device_lost` marker record that carries the same `samples`, a torn last line the tail reader skips) reads as
  "not advancing" or, worse, a stuck tail reads as advancing never. It is a proxy for "audio bytes reached disk".
  Whether it misreported on 25/26 Sep: UNVERIFIED (no poll rows read yet).
- Fix: `tape_advancing` = `tape.pcm` size grew since the previous poll (stat of the segment's `tape.pcm`, cheap, no parse).
  Keep the idx tail only for `samples`/level fields. Missing file or first poll = false (unchanged).
- Test (fails before, passes after): fake segment whose `tape.pcm` grows while `tape.idx` is not appended → expect true
  (before: false); and idx appended with a device_lost marker but pcm not growing → expect false. In
  `Tests/TapeCoreTests` beside `RoomAudioInputCommandTests` (uses `R4FakeTapewriter`).
- Risk: low. A pcm that grows with silence still reads "advancing"; SILENT_WHILE_RECORDING (lib/bench-bus-constants.ts:601-606)
  already covers that and needs `tapeAdvancing === true`.

## 2. poll reports device_lost
- Today: `device_lost` exists only in `tape.idx` (`tapewriter/AudioRing.swift:6`, `Recorder.swift:278`); `InstallPollFields.swift`
  has no field for it. The desk sees only `tape_advancing=false`, indistinguishable from an encoder stall
  (`ENCODER_STALLED`, lib/bench-bus-constants.ts:~634).
- Fix: new optional poll field `device_state` ∈ {`ok`,`lost`} derived from the last non-`none` discontinuity marker in the index
  tail (a `device_lost` with no later `resumed` ⇒ `lost`) plus `AudioInputDevices.list()` not containing the configured UID.
  Server: a `DEVICE_LOST` flag in `lib/bench-bus-constants.ts` (needs a server change + migration check for the poll column;
  **open question Q3**: may 0.1.25 ship with the server field behind an unknown-field-safe ignore, or must the server land first?).
- Test: `InstallPollFieldsTests` encode/omit rules; tail fixture with device_lost-then-resumed vs device_lost only.
- Risk: medium (wire change). Additive, omitted when unknown, like every other field.

## 3. same-uid set_audio_input is a no-op
- Root cause (VERIFIED): `RoomEngine.swift:3138 guard uid != previousUID else { return nil }` in `switchRecordingDevice`; the ack is
  `ok:true` with `appliedDeviceUID` set (l.~3095), nothing reopens.
- Fix: when `uid == previousUID` and a capture is running, close and reopen the segment exactly as the different-uid path does
  (`stopCaptureAndPublishFinal(.pause)` then `startCapture(.reconciliation)`); ack says `reopened:true`. Idle/paused: no-op, ack `reopened:false`
  (honest, not "applied").
- Test: fake tapewriter, same uid command while recording → expect old process stopped, new segment dir opened, same session id, piece
  index continues (fails today: same segment, one process). Existing rollback path covers a reopen that fails.
- Risk: medium: it is the one command that interrupts audio. Must not be usable by the auto-recovery path in a loop (see 5).

## 4. DEVICE_MISSING may not fire
- Root cause (VERIFIED, two halves): app `MachineFacts.swift:120 inputDeviceName(forUID:)` returns nil when the device is not attached
  (comment: "sends absence so the server keeps the last true name"). Server `lib/bench-bus-constants.ts:~620-626` raises DEVICE_MISSING only when
  `input.inputDeviceName` is truthy AND the `input_devices` list lacks that name. So the moment the device vanishes, name=nil and the flag
  can never fire; it fires only for a device that is listed-but-different. This is the defect, not a race.
- Fix: send the configured UID's last known name from a small persisted cache (or send `expected_device_uid`); server compares UID/name to list.
  Server side alternative with no app change: use the row's last stored `input_device_name` when the poll's is null and `input_devices` is an array.
  **Q4: which side? I recommend the server side first (no build, works on every fleet Mac already on 0.1.20+).**
- Test: `tests/unit/bench-room-states.test.ts` (near l.146): stored name X, poll name null, devices list without X → DEVICE_MISSING (fails today).
- Risk: low; false positive if a device is genuinely renamed (then DEVICE_CHANGED already applies).

## 5. Device-loss recovery, no manual restart
- Already works (VERIFIED on the 25 Sep tape): same-UID re-enumeration → tapewriter reopens within 5 s.
- Gaps (each UNVERIFIED until the 26 Sep evidence is read):
  a. UID changes on replug (the C270 UID embeds a location field, `…C270 HD WEBCAM:87C03150:3`); `AudioDevices.selected(uid:)`
     (`tapewriter/AudioDevices.swift:13`) throws forever ("input device not found"), the loop retries the dead UID for ever.
  b. Device listed but `engine.start()` throws or callbacks never resume: loop retries every 5 s but never escalates to a new tapewriter process.
  c. macOS not listing the device (25 Sep): nothing software can do; must be surfaced (item 2/4), not silently retried.
  d. The engine layer (`RoomEngine.swift:3322 finishUnexpectedCaptureIfNeeded`) only acts when the tapewriter PROCESS exits, so a
     tapewriter stuck in its retry loop is invisible to it.
- Fix design: (i) in tapewriter, when the configured UID is absent for > N s and exactly one input device matches the configured
  name prefix (text before the location field) re-bind to it and log `rebound uid`; never re-bind to a different product. (ii) engine
  watchdog: `device_state == lost` for > 120 s AND configured device listed again ⇒ one `restartCapture` (same path as item 3), at most once per 10 min. (iii) no new
  config write unless the rebind is confirmed by 30 s of growing tape.pcm.
- FIRST STEP (before any code): read the 26 Sep OPD 4 `tapewriter.log` + `tape.idx` tail from the Mini (minibot, read-only; needs Fable's routing)
  to classify the 26 Sep freeze as a/b/c. **Q1.** I will not design (i)/(ii) further until then.
- Test: tapewriter `Recorder` is hardware-bound; add a seam (`AudioDeviceSource` protocol: list, isAlive, open) and test rebind/no-rebind
  with a fake source: fails today (no rebind exists). Hardware probe stays opt-in like the R4 one.
- Risk: HIGH (touches the live capture loop on every room). Rollout order below applies fully.

## 6. Auto-start at clinic open
- Where clinic-open time comes from today: **nowhere.** Grep of `db/migrations`, `lib/bench*`, `db/schema.ts` and the recorder for open_time /
  opens_at / hours / schedule finds no per-room open time. Days start only by a desk `start_day` command (`BenchCommandKind.startDay`,
  `BenchClient.swift:180`) or by resuming an active session at launch (`RoomEngine.swift:1167 run()`).
- Proposal: a per-room schedule held server-side (source of truth, editable without a build), delivered in the poll response and cached in
  `config.json` so a Mac that is offline at open still starts. Default when a room has none: **Mon-Sat 09:00-18:00 Asia/Kolkata, no Sunday**.
  App behaviour: at open, if phase is idle and no `paused_by_desk`/`end_day` for today, the engine issues its own `start_day` (same code path,
  command id `auto-<date>`, journaled like a desk one so re-launch does not double-start). Desk `end_day`/pause after open is honoured for the day.
- fleet-watch: alert if now > open + 10 min and the room has no open session. Rule is computed at read time from the schedule and a fresh clock
  (repo rule: absence is derived at read time), never stored.
- V must confirm (**Q2**): (a) the default hours, per room and per weekday (Cardiology, OPD 3/4/5, ORB3, Home Office differ?); (b) Sundays off;
  (c) whether the app may auto-start on the very first launch after an update, or only when a schedule is present; (d) what a desk `end_day` means
  after open (my proposal: stays ended until next open).
- Test: engine with an injected clock: idle at 09:00 → one start; already ended by desk → none; restart at 09:05 → one start not two.
  Server: fleet-watch rule unit test with fixed `now`.
- Risk: medium-high: it is the first time the app starts the day by itself. Home Office only until the desk-end semantics are seen working.
