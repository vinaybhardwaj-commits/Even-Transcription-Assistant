`guardPaidEngine` has exactly ONE production call site: `lib/mcp/tools/bench.ts:1975`. Every other path to a transcription call is ungoverned by it. Enumerated, each proved by running:
1. `scribe_transcribe_range` sync — GUARDED (bench.ts:1975). 2. same tool `async:true` — refuses a named non-whisper engine (bench.ts:1932). 3. `scribe_extract_audio async` → `stitch` — no engine, no transcription (bench.ts:1029). 4. `room_window` job `segment` — whisper only, free (room-drain.ts:660). 5. `room_window` job `engine` — **routed engine, NO guard, no `recordPaidCall`** (room-drain.ts:1044). 6. `drainRoomWindow`/`drainRoomWaitingWindows` → enqueues that job (room-drain.ts:444-457), up to 12 windows per press. 7. `route_transcribe` job — `route` is the Mini's own tunnel, genuinely free (adapters/route.ts:63). 8. **`runFanoutForEncounter`, `allowPaid` defaulting TRUE, no guard** (fanout.ts:92,136) — live on the doctor path (`app/[slug]/api/encounters/[id]/process/route.ts:769,1246`); PRE-EXISTING, not from this diff. 9. indic-live / indic-note-assist / tuning-fork — fixed free local engines.

**AND THE GUARD IS INERT AS THE DATA IS SEEDED.** "Paid" is derived from `stt_engine.cost_per_min_usd > 0` (paid-engines.ts:45). Every paid engine is seeded `is_paid = true, cost_per_min_usd = NULL` — sarvam, deepgram, elevenlabs, ekascribe (`0018_stt_engine.sql:24-38`) and gemini (`0073:58`, NULL *by design*, Vertex bills per token). `paidEngineInfo` maps NULL → `paid:false` (paid-engines.ts:44). The Builder's test passes only because its mock supplies `sarvam: 0.02` (c1b-paid-engine-guard.test.ts:36), a price no migration sets. `fanout.ts:32` reads the same NULL as *paid-but-unpriced*; two modules disagree about NULL. INFERRED — no live DB here; the Orchestrator must read the live `cost_per_min_usd` for sarvam/gemini. If it is NULL in production, the guard stops nothing.
**Cap.** Per-call only; no cumulative budget exists, so N calls each ≤600 s bill N×600 s — by design (paid-engines.ts:22-31), but "cannot be bypassed" is true only per call. Separately, on the single-chunk branch the guard measures the requested window (`rangeMs`, bench.ts:1974) while **the WHOLE 5-minute chunk is sent to the engine** (bench.ts:2062-2066; the code says so at :2095, "trimming is v1.1"; 5 min = use-room-recorder.ts:72). ## TARGET 2 — the step budget. YOUR PREMISE WAS RIGHT ABOUT THE RISK, WRONG ABOUT THE MECHANISM.
`MAX_STEP_MS` (200 s) is **never enforced on a running step** — its only use is admission control, `runner.ts:149`. Nothing kills `segment` at 200 s. The real ceilings are whisper's own `timeoutMs: 180_000` (room-drain.ts:660), `LEASE_MS` 240 s (types.ts:38) and the route's `maxDuration = 300` (app/api/jobs/run/route.ts:24), which does kill.
Worst case for `segment`, with evidence: whisper on the full 900 s window is hard-bounded at **180 s** by its own timeout, and a timeout is deliberately NOT retried (`isRetryableWhisperError`, whisper.ts:185-189; the reasoning at whisper.ts:148-152 names the 362 s figure and rejects it). So the normal ceiling is ~180 s + R2 GET of the full clip + `buildTurns` + `writeWindowCues` (HTTP to own origin) + one shadow INSERT. The shadow is **one INSERT, not a second inference** (room-drain.ts:713-730) — your "~180 s at 0.2x" concern does not compound there. **But 180 s of a 200 s budget leaves ~20 s for all that I/O, and a slow retryable 5xx (not a timeout) still yields ~362 s: 180 + 2 s backoff + 180.** Beyond 240 s the lease expires and a second runner may re-claim and redo the work (the write is safe — `lease_lost`, runner.ts:90 — the *work* is not). The "0.2x realtime" claim is an unsourced code comment (room-window.ts:8); no measurement exists in this repo. I did not load the production Mini to measure it.
**Pre-flight duration check: FEASIBLE and cheap.** `audio_seconds` is already on the job row from `prepare` (room-drain.ts:626) and is read by `segment` before any work. A guard there — refuse with a named `segment_would_exceed_budget` when `audio_seconds × factor + margin > MAX_STEP_MS`, factor from an env var — gives the predictable refusal instead of a lease-expiry mystery. Reported, not fixed.

## CORRECTION TO THE BRIEF
"No drain cron" is true of `/api/admin/bench/drain`, but `vercel.json` runs **`/api/jobs/run` every minute**. Dormancy rests on nothing *enqueueing* a `room_window` job, not on the absence of a cron: once an operator enqueues one, the cron executes the whole pipeline — routed engine included — within a minute. Migration `0084` (routing → `route`) is self-marked NOT SAFE TO APPLY and is unapplied; `route` has no `stt_engine` row, so `resolveRouting` would return null for it anyway (routing.ts:25-27).

**SAFE TO MERGE DORMANT: yes.** Nothing auto-enqueues a room window, routing stays on sarvam, 0084 unapplied, gate green, and every FAIL above is a latent property of code that does not run until someone presses a button.
**SAFE TO RESTART STT: not yet.** Three blockers, in order: (1) settle what NULL `cost_per_min_usd` means and price sarvam/gemini, or derive "paid" from `is_paid` with a conservative rate as fanout already does — until then the guard stops nothing; (2) put the guard on the drain/job path, which today reaches a paid engine by routing inheritance at 900 s, above the cap and unaudited; (3) add the pre-flight duration refusal to `segment`, since nothing bounds it at 200 s and a 240 s overrun re-runs the work.
